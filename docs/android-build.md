# Android Build

CLAYBA Driver (and, by the same mechanism, CLAYBA passenger) can be built
two ways: **locally**, via the native Gradle toolchain, or via **EAS
Cloud**. Local builds exist specifically so a QA APK is never blocked on
EAS's account-level build quota (see the P0 local-build-pipeline report)
— use Pipeline A by default; Pipeline B is for real store submissions
where EAS's managed signing/credentials matter.

## Pipeline A — Local QA APK Build (no EAS Cloud)

```
pnpm driver:android:apk
pnpm passenger:android:apk
```

Runs `scripts/build-android-local.mjs`, which:

1. validates the local environment (JDK, `ANDROID_HOME`)
2. validates the app's `.env.local` has all six required
   `EXPO_PUBLIC_FIREBASE_*` values (missing this is exactly what shipped
   the white-screen `playba-driver-v0.1.0.apk` — see the P0 report)
3. validates a release signing keystore exists (see "Signing" below) —
   never generates one silently
4. `expo prebuild --platform android --no-install` (never `--clean` —
   see "Native Android project" below)
5. `cd android && gradlew assembleRelease`
6. locates the produced `.apk`, prints its path/size/SHA-256

The APK lands at
`apps/<app>/android/app/build/outputs/apk/release/app-release.apk`.
Publishing it to the DEV download section (copying into
`apps/web/public/downloads/android/`, updating `latest.json`, rebuilding
and deploying `hosting:web`) is a deliberate separate step — a QA build
never silently becomes what the live download button serves.

### Prerequisites

- **JDK 17** (matches this project's `react-native`/Expo SDK 52 — do not
  arbitrarily use a newer JDK). `keytool`/`jarsigner`/`java` all ship
  with it.
- **Android SDK** with `platforms;android-35` (this project's
  `compileSdkVersion`), `build-tools;35.0.0`, and `platform-tools` (for
  `adb`). If you have Android Studio installed, its bundled SDK usually
  already has these, typically at
  `%LOCALAPPDATA%\Android\Sdk` — set `ANDROID_HOME` to it. Missing a
  platform/build-tools version can be installed with the SDK's own
  `cmdline-tools\latest\bin\sdkmanager.bat "platforms;android-35"
"build-tools;35.0.0"` (accept the license once with `sdkmanager
--licenses`).
- **Node + pnpm**, already required for the rest of this monorepo.

The script auto-detects `JAVA_HOME`/`ANDROID_HOME` from common install
locations if the env vars aren't already set, but setting them yourself
is more reliable across machines.

### Native Android project

`apps/<app>/android/` is **generated by `expo prebuild`, not hand-authored
source** — same philosophy as a fresh `create-expo-app` project, which
gitignores `/android` and `/ios` by default. It is _not_ committed to
this repo (see `.gitignore`). Re-running `expo prebuild --platform
android` (without `--clean`) after an `app.json` change regenerates it
in place and — confirmed empirically — preserves the hand-added
`signingConfigs.release` block in `android/app/build.gradle` (Gradle
files aren't part of Expo's "fully regenerated every time" set the way
`AndroidManifest.xml`'s managed sections are). **Never run `expo
prebuild --clean` for these apps without re-checking that signing block
survived** — `--clean` deletes and fully regenerates `android/`, which
would remove it.

### Signing

`0.1.1`'s signing identity is managed by EAS Cloud's remote credential
store — there is no non-interactive way to export it locally (`eas
credentials` is an interactive-only TUI). Local QA builds therefore use a
**separate, genuine DEV/QA release keystore**, generated once with the
JDK's own `keytool` and stored **entirely outside this repository**
(default `~/.clayba-driver-keys/keystore.properties` +
`.keystore` file; override the path with the
`CLAYBA_DRIVER_KEYSTORE_PROPERTIES` env var). `build.gradle`'s `release`
signing config reads store/key passwords from that external properties
file at build time and **fails the build with a clear error** if it's
missing — it never falls back to the debug key or invents a password.

Because this is a different signing identity than `0.1.1`, Android will
refuse to install a locally-built APK over an existing `0.1.1` install —
**uninstall the old app first**. This is expected, not a bug.

To generate a new DEV/QA keystore (only if `~/.clayba-driver-keys/` — or
your override path — doesn't already have one):

```bash
keytool -genkeypair -v \
  -keystore ~/.clayba-driver-keys/clayba-driver-dev-release.keystore \
  -alias clayba-driver-dev -keyalg RSA -keysize 2048 -validity 10000 \
  -dname "CN=CLAYBA Driver DEV, OU=Engineering, O=CLAYBA, L=Unknown, ST=Unknown, C=US"
```

then write `~/.clayba-driver-keys/keystore.properties` with `storeFile`,
`storePassword`, `keyAlias`, `keyPassword` (note: modern `keytool`
defaults to PKCS12 keystores, which require `keyPassword` to equal
`storePassword` — a separate key password is silently ignored with a
warning). **Never commit this file or the `.keystore` — both must stay
outside git**, and the passwords must never appear in any report/log
that gets committed or shared.

### Static verification after a build

With `ANDROID_HOME` set:

```bash
"$ANDROID_HOME/build-tools/35.0.0/aapt.exe" dump badging <apk>       # package/versionName/versionCode/label
"$ANDROID_HOME/cmdline-tools/latest/bin/apkanalyzer.bat" apk summary <apk>
unzip -p <apk> AndroidManifest.xml | strings | grep -i <sanity checks>
```

A raw string search of the extracted `classes*.dex`/JS bundle for the
real Firebase project id (and the _absence_ of any service-account/admin
credential pattern) is the same technique used to diagnose the original
P0 white-screen bug — worth repeating on every new build, not just when
debugging.

## Pipeline B — EAS Cloud Build

`apps/driver-app` and `apps/passenger-app` each have an `eas.json` with
four build profiles:

| Profile          | Distribution         | Android output                                                                                          | `APP_ENV`     |
| ---------------- | -------------------- | ------------------------------------------------------------------------------------------------------- | ------------- |
| `development`    | internal, dev client | APK                                                                                                     | `development` |
| `preview`        | internal             | APK                                                                                                     | `staging`     |
| `production`     | store                | AAB (Play Store submission format)                                                                      | `production`  |
| `production-apk` | store                | APK (extends `production` — same version/env, different package format for direct-install distribution) | `production`  |

**Firebase config for EAS builds**: `eas.json`'s `env` blocks only set
`APP_ENV` — they never contained `EXPO_PUBLIC_FIREBASE_*`. Local dev (and
Pipeline A above) gets those from each app's gitignored `.env.local`, but
an EAS cloud build has no access to that file, so it needs the same
values configured as **EAS project environment variables** instead:

```bash
eas env:create --environment production --name EXPO_PUBLIC_FIREBASE_API_KEY --value ... --visibility plaintext
# repeated for AUTH_DOMAIN/PROJECT_ID/STORAGE_BUCKET/MESSAGING_SENDER_ID/APP_ID, for both production and preview
```

Missing this is exactly what shipped `playba-driver-v0.1.0.apk` (CLAYBA
Driver P0): `initializeApp()` ran with an `undefined` config and threw
during module evaluation, before React ever rendered a frame. Run `eas
env:list --environment production` before any release build to confirm
these are actually set. These are Firebase's public client values (safe
by Firebase's own security model), not secrets — `--visibility
plaintext` is correct.

`"appVersionSource": "local"` means EAS reads `version`/`android.versionCode`
straight from each app's `app.json` — not a remote counter.
`production`'s `"autoIncrement": true` bumps `versionCode` locally by 1
if a build is re-run without a version bump in between.

```bash
cd apps/driver-app
eas login                                               # once, interactively
eas build --platform android --profile preview          # staging APK
eas build --platform android --profile production       # store AAB
eas build --platform android --profile production-apk   # direct-install APK, same version
```

**Known limitation**: EAS's free tier caps Android builds per account
per month; once exhausted, every `eas build` invocation fails with an
explicit quota message (not a silent hang) until the monthly reset or a
plan upgrade. Pipeline A exists precisely so a QA APK is never blocked on
this.

## Versioning and release notes

- **Versioning**: `RELEASE_VERSION` in `packages/types/src/version.ts`,
  mirrored into both `app.json`'s `expo.version` — see docs/versioning.md.
- **Build number**: `ANDROID_VERSION_CODES.driver`/`.passenger`, mirrored
  into `app.json`'s `expo.android.versionCode`.
- **Release notes**: `release-notes.md` inside each generated
  `/release/v{version}/` folder — see docs/release-process.md.
